# Рефлексия по практике 4: Инженерия среды агента

## 1. Что помогло

1. **Единый контракт проверок (`scripts/check.sh` и `AGENTS.md`):**
   Фиксация единого скрипта проверок полностью сняла неопределенность с запуском тестов и линтера. Агент не пытался гадать параметры `go test` или `go build`, а сразу опирался на один доверенный источник правды. Правило в `AGENTS.md` «не ослаблять проверки» предотвратило типичную проблему, когда LLM при падении теста просто удаляет упавшее утверждение.

2. **TDD-скилл (`test-driven-development`):**
   Пошаговая методология Red-Green-Refactor заставила четко сформулировать граничные условия до написания логики валидации. Фаза Red наглядно продемонстрировала ожидаемое падение (нереализованный метод), а фаза Green дала минимальный чистый код без оверинжиниринга.

3. **Собственный MCP (`url-inspector`):**
   Вынесение сетевой проверки веб-страниц в отдельный MCP-сервер позволило протестировать инструмент изолированно через протокол JSON-RPC (stdio). Обработка ошибочного ввода (запрещенные локальные адреса `localhost`, неверные схемы, таймауты) показала устойчивость — сервер не крашится, а возвращает структурированный `isError: true` с понятным описанием.

4. **Изоляция в Git Worktree и Subagent Review:**
   Реализация фичи B в отдельном каталоге `project-p4-b` дала полную уверенность, что стабильная фича A не повреждена. Запуск субагента-ревьюера по профилю `.opencode/agents/tester.md` с правами «read-only» помог объективно оценить diff со стороны: субагент подтвердил отсутствие регрессий и обратил внимание на общий бюджет таймаута для последовательных операций.

## 2. Что мешало и вызвало сложности

1. **Особенности сетевого клиента в тестах:**
   В клиенте Telegram метод `DoRequest` жестко использует схему `https://`. При попытке замокать Telegram API через стандартный `httptest.NewServer` (который слушает обычный HTTP) запросы не проходили. Пришлось переключиться на `httptest.NewTLSServer` и настроить `http.DefaultTransport` на доверие самоподписанному сертификату теста.
2. **CGO и SQLite:**
   Драйвер `mattn/go-sqlite3` требует включенного CGO. При запуске тестов и сборки агенту было критично явно помнить про `CGO_ENABLED=1`, что было закреплено в `AGENTS.md`.

---

## 3. Где потребовалось вмешательство человека (Human-in-the-Loop)

1. **Проектирование поведения при частичном сбое в `SendRandom`:**
   В фиче B при выдаче ссылки выполняются два действия: отправка сообщения в Telegram и удаление ссылки из базы (`storage.Remove`). Возник вопрос: что делать, если сообщение успешно ушло пользователю, но база вернула ошибку при удалении? Было принято решение: не возвращать ошибку выше (иначе пользователь получил бы сообщение об ошибке, уже видя ссылку), а записать предупреждение в лог.
2. **Определение допустимых границ таймаута:**
   Выбор 5-секундного таймаута (`defaultOperationTimeout`) для операций базы данных потребовал инженерного решения, учитывающего блокировки SQLite при высокой нагрузке.
3. **Разделение прав субагента:**
   Ограничение прав профиля `tester.md` (запрет на редактирование файлов) предотвратило ситуацию, когда ревьюер пытается «исправить» код вместо указания на проблему.
